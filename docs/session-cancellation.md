# HTTP 会话写入与取消

聊天提交、会话导入和删除共用每会话 turn 锁。锁覆盖历史读取、模型调用及最终存储；不同会话仍使用各自的 turn 锁，底层共享存储保持原有串行方式。

SQLite 工作通过 `spawn_blocking` 执行。取消等待它的异步任务不会撤销已经派发的工作；工作可能尚在阻塞线程池排队、等待 store mutex，或已经等待 SQLite 的写锁。因此，写入阶段必须把 turn 锁所有权交给实际存储工作，直到写入和原有持久化操作成功或失败后才释放。HTTP 聊天及旧入站 webhook/HEARTBEAT 的公共提交函数要求传入锁；HTTP 导入和删除使用相同的存储入口。

这样，后续同会话聊天、导入和删除只能在前一个存储结果确定后读取或替换历史。被取消的写入不会越过后续删除或导入；失败也会释放锁，原有 `session_storage_error` 和导入冲突响应继续有效。数据库 schema、SQL busy timeout、模型预算及工具权限没有变化。

客户端未收到成功响应时，结果可能已经落盘，也可能仍在执行。现有 GET/export 是快照读取，不取得 turn 锁；一次查询看见旧历史不能证明待处理写入已经结束。保留已知 session ID 并人工核对，不要因连接断开自动重发聊天。此锁修复不提供 HTTP 请求收据、自动恢复模型/工具循环，或副作用重放资格。网络断开也不保证 Axum 一定取消 handler；具体协议路径须独立验证。

`session_turn_tests.rs` 使用实际 SQLite 文件和真实 handler/公共提交函数验证六个边界：聊天提交、HTTP 导入、HTTP 删除、被拒绝的写入、单槽阻塞线程池排队及第二个 SQLite 连接的写锁争用。测试以实际 worker 的派发/持锁屏障定位取消，没有用模型延迟代替数据库状态；取消后确认同会话不能进入，放行后确认最终历史、锁释放与重新打开数据库的持久结果。四个原有路径在修复前全部复现提前释放，修复后纳入两平台完整 Cargo CI。

这是 HTTP/Web 真流式接线的前置修复。现有 HTTP SSE 仍然在完整回复后分块，Web 未增加流式入口；CLI 单次真流式仍按[独立合同](cli-streaming.md)验收。接通 HTTP/Web 仍需明确有界发送、客户端取消与服务停机、持久请求身份及未确认结果的核对入口。
