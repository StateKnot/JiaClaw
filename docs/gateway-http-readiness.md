# 关闭夹具先核对实际 HTTP 就绪

`tests/gateway_shutdown.py` 的 `Fixture.start` 在原十五秒启动截止内等待原网关 `/health` 的完整 `200 {"status":"ok"}`，随后才进入原四条慢下载连接的三秒响应头准备窗口。每次 HTTP 探测最多使用原 200 毫秒连接等待或剩余启动时间，两者取小；响应完成后再次核对同一十五秒截止。没有为重试探测重新领取启动期限。

原夹具只检查 TCP 可连接。真实 `listen` 成功后、应用开始处理 HTTP 前，操作系统已经可以排队连接；这不能证明应用就绪。本批使用同一冻结产品、真实 `listen` 返回后的受控 3.25 秒暂停，原夹具两次在原 `recv(512)` 三秒窗口超时，后端尚未收到该 GET；修订夹具在同一十五秒内等待实际 HTTP 响应，随后四条原慢下载连接正常收到响应头。探测只访问网关自己的健康路由，不调用模型或后端业务。

完整七组仍执行原三秒响应头、五秒关闭回执、共享十五秒排空、十七秒等待、真实重启、未知 hold、迟到正文和迟读日志反例。七个独立夹具加两次真实重启，共产生九份有类型的 HTTP 就绪收据；只核对完整原命令中的实际收据，不能以启动前缀补完整关闭合同。

该改动只修正夹具前置条件，不改生产网关、权限、hold、模型工具、CI 的四十／六十分钟上限或任何原期限。受控本机启动窗口不是 Hosted Intel 的等价环境；旧 Intel 响应头超时、Ubuntu 四十分钟取消、容器公共镜像 HTTP 429 的唯一历史原因仍未知，各自证据保留。新固定 head 必须独立完成全部原合同与新增就绪证据，不借旧 head 或本机验收。
