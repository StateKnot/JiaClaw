# Personal-Key exact webpage tasks

A personal user can explicitly allow the existing `web_fetch` on one task. The administrator must first configure the same default-off destination grant in the tenant's native HTTP service and its gateway backend. This enables page text retrieval through the original model/tool/receipt loop; it does not provide an Agent browser, login session, script execution, screenshots or autonomous browsing.

```json
{"http":{"tenant_web_fetch":{"urls":["https://example.com/report","https://example.com/report-final"],"allow_private":false}}}
```

Native configuration uses `http.tenant_web_fetch` (`[http.tenant_web_fetch]` in TOML). Set `tenant_web_fetch` to the identical object on the corresponding `backends[]` entry in the gateway config. Existing tracked HTTP/gateway configuration and per-user tokens remain required. Configure grants before starting both services; changing or withdrawing one requires stopping and restarting both. No public endpoint edits permissions.

A grant contains 1–8 sorted unique complete ASCII HTTP(S) URL strings, at most 1024 bytes each. Each URL has a lowercase DNS/IPv4 host, optional nonzero decimal port without leading zeros, and an explicit `/` path. No userinfo, fragment, backslash, whitespace, control bytes, raw Unicode host/path or IPv6 literal is accepted. Unicode paths can use percent encoding. Queries are part of the exact grant and may contain private data. Grants are exact strings, not host/prefix grants, content identities, DNS pins or provenance attestations. The application does not probe destinations at startup.

The restricted schema accepts only a granted `url` and optional integer `max_chars` in 500–50000 (default8000). Direct execution also validates those fields without trimming or clamping. Every resolved redirect target must independently equal a granted URL **before** the original HTTP client sends the next request. A granted start URL does not authorize its redirects, other paths or another user's destinations. Public-only grants retain the original DNS/private-address checks. Delegating private access requires both the explicit grant flag and the original administrator tool override; it allows requests from that tenant's network environment and should be limited to destinations intended for that user. This is cooperative application permission, not an independent OS/network ACL or DNS-rebinding defense.

Permission protocol1 is separate from SSE2. The complete descriptor is `protocol, urls, allow_private, max_capture_bytes, max_body_bytes, timeout_seconds, max_redirects, max_chars, policy_sha256`. Its SHA256 is UTF8 JSON of `[1,urls,allow_private,1048577,1048576,15,5,50000]`. The native and gateway services compare the complete descriptor at startup and before every new admission, before creating the gateway identity/hold or sending the backend PUT. Only a task selecting `web_fetch` includes `web_fetch_policy_sha256`; old submissions without it keep their old request hashes. Old UUID GET/same-body PUT only return original facts and do not redispatch after permission changes.

The workbench validates the complete descriptor and SHA using secure-context WebCrypto, displays every URL with `textContent`, and leaves the checkbox unchecked. Explicit Send captures the current permission. Identity changes clear private URLs/results/selections; late old Crypto cannot restore them or dispatch. Readonly Keys can inspect their original authorized facts, but cannot submit new tasks. Revoked/cross-user Keys retain the original rejection. No browser storage, automatic polling, implicit HTTP/model request, new public route, model tool, Store or second reader is introduced. Channel and cron tasks retain their original two tools.

The original lazy HTTP reader, five manual redirects, 15-second deadline, 1MiB+1 application capture / 1MiB retained raw prefix, text extraction and character truncation remain. These are not OS memory/wire-byte limits or hard preemption. TLS, DNS, client buffering, headers, extraction and scheduling have their original limits. No new cookies, login credentials or headers are accepted. The original client/environment networking behavior remains. URL and fetched text can reach the user's configured model and persisted messages; ambient SOUL/USER/MEMORY still enter prompts independently. Pages are untrusted instructions, not an injection-isolated data channel. A GET can be logged or have server-side effects; tool errors/timeouts therefore remain **Unknown**, and an unapproved redirect after a request may have been sent leaves the original `needs_review` result. Cancellation prevents future dispatch, does not revoke an already sent request, preempt its blocking thread, or clear unknown holds. Fixture success does not certify suppliers, public TLS, business answer quality, learning, durable execution or true Agent browsing.
